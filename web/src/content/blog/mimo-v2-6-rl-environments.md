Xiaomi released MiMo-V2.6 last week. MiMo-V2.6-Pro is a 1.02T-parameter mixture-of-experts model with 42B active parameters, and it scores close to Claude Opus 5 and GPT-5.6 Sol on several agent benchmarks. Along with the weights, Xiaomi released the reinforcement learning environments it trained on: [7,780 tasks](https://huggingface.co/datasets/XiaomiMiMo/MiMo-V2.6-RL-oss), their graders, the [training code](https://github.com/XiaomiMiMo/verl), and 7.5 TB of Docker images.

Labs rarely release this part. So I went through all of it, and I built an [explorer](/mimo-rl/) where you can open every task, read its grader, and follow each claim in this post back to the rows behind it.

This post answers six questions:

1. What is in the dataset?
2. How is each task graded?
3. How do you get a strong model from so few tasks?
4. What does the team care about?
5. What is wrong with it?
6. What is it worth?

## What is in the dataset

The release has five configs on Hugging Face. The general config holds two different task families, so I split it and count six parts.

| Part     | Tasks | What the agent does                                                   | Grader                               |
| -------- | ----- | --------------------------------------------------------------------- | ------------------------------------ |
| Code     | 2,698 | Changes a real repository so that hidden tests pass                   | Unit tests                           |
| Webdev   | 2,093 | Builds a static website from a short request                          | Vision model comparing screenshots   |
| Cyber    | 1,000 | Writes an input that crashes a C or C++ program in one named function | String match on the sanitizer report |
| Music    | 1,000 | Composes a piece in ABC notation                                      | Statistical scorer                   |
| General  | 925   | Does office work with documents and mock business software            | Rubric, mostly an LLM judge          |
| Terminal | 64    | Fixes or analyzes code and data in a terminal                         | Tests and an anti-cheat guard        |

<a href="/mimo-rl/"><img src="/assets/img/blogs/mimo-rl/fig-multiples.png" alt="Six small maps of every prompt in the dataset, one per part" width="100%"></a>

Each dot above is one task, placed so that similar prompts sit close together. The music and cyber tasks form tight clusters because their prompts follow templates.

### Code

Each of the 2,698 tasks is its own Docker image with a repository at an old commit and a problem statement. After the agent stops, the grader adds hidden test files and runs them. Most tasks are Python (1,237) or Go (741), and pytest and go test run 64% of them. The tasks come in four test formats, which look like four different build pipelines. The images take 6.7 TB, with a median of 3.1 GB each.

### Webdev

The 2,093 prompts read like real user messages, e.g., "Build me a static React website for a tutoring cafe called Study Bites, like a restaurant site but for group lessons, brutalist style." 1,658 are in English, 258 in Arabic and 93 in Turkish. 85% of them name a well-known product as a style model, e.g., "feel premium and clean like Stripe". Each brand appears about 95 to 110 times and each framework about 190 to 210 times, so the prompts were most likely generated by sampling from fixed lists.

### Cyber

The 1,000 tasks are bugs from [ARVO](https://github.com/n132/ARVO), a public set of reproducible OSS-Fuzz crashes, in 176 C and C++ projects. The most common are nDPI (70 tasks), FFmpeg (55) and ImageMagick (52). The agent gets the source code and the compiled fuzzing binary. Heap buffer overflows are 39% of the tasks.

### Music

The 1,000 prompts ask for a piece in one of 79 genres, from Bach chorales to reggaeton, half in Chinese and half in English. Each prompt names a key, tempo, meter, instruments, number of voices and length.

### General

These 925 tasks are the most interesting part. Each one drops the agent into a fake company in one of 16 industries, with a folder of documents and 3 to 18 mock versions of real business software. A task has a median of 13 documents, mostly spreadsheets, Word files, CSVs, PDFs and slides.

The mock software runs as MCP servers backed by SQLite, in a separate container the agent cannot reach directly. The English tasks mostly imitate Microsoft, ServiceNow, Oracle, SAP and Workday. The Chinese tasks imitate Chinese enterprise software such as Yonyou, Weaver and FanRuan. Across all 925 tasks there are 6,132 mock tools with 44,633 functions.

Most tasks, 78%, only ask the agent to find information and report it. The rest ask it to change records.

### Terminal

There are 64 tasks in the Terminal-Bench format, mostly in software, ML and security.

## How each task is graded

<a href="/mimo-rl/#/grading"><img src="/assets/img/blogs/mimo-rl/fig-graders.png" alt="Share of tasks by grader type" width="100%"></a>

61% of the tasks are graded only by code, and 39% need a model judge. Here is how each grader works.

- A code task passes when the hidden test script exits with zero. In 276 tasks, the script runs the old tests, which must keep passing, and then the new tests, which must now pass.
- A cyber task passes when the new crash has the same bug type as the original report and the same top stack frame from the project's own code. It is a plain string match, with no model involved.
- A terminal task runs test scripts. A guard runs first and gives zero if the agent planted files that could fool the tests, such as a `conftest.py`.
- A music piece first has to pass a format check. Then a program scores how close 18 statistics of its notes, such as rhythm, harmony and range, are to human music.
- A website is rendered in a browser, and a vision model compares the screenshots of all rollouts for the same prompt and picks the better ones. A page whose scripts crash or hang gets zero, whatever it looks like.
- A general task is scored with a rubric of 2 to 10 items, with a median of 5.

<a href="/mimo-rl/#/general"><img src="/assets/img/blogs/mimo-rl/fig-items.png" alt="Rubric items in the general tasks by tier and judge" width="100%"></a>

There are 5,125 rubric items in the general tasks. An LLM judges 87% of them, and code checks the rest. Every LLM item sees only the agent's final message. The judge gets a "pass anchor" that spells out the expected facts, and it must answer 0 or 1 with no partial credit. Each item is marked critical, important or sanity. A sanity item checks that the agent did not break anything.

One small trap for anyone using the data: every row labels its reward style as "rule", including the 3,018 tasks that a model grades. You cannot use that field to tell graders apart.

## How do you get a strong model from so few tasks?

7,780 tasks sounds small next to the millions of examples used in supervised fine-tuning. But in RL, the model learns from its own attempts at each task, and every attempt produces new training data.

The numbers from the [paper](https://huggingface.co/XiaomiMiMo/MiMo-V2.6-Pro-RL/blob/main/MiMo_V2_6_technical_report.pdf) show how much practice each task gives:

- Each RL step used 1,568 tasks with 16 attempts each, so 25,088 rollouts per step.
- Each rollout was about 110K to 150K tokens long, so one step trained on 2.7B to 3.7B tokens.
- The run lasted 30 steps. That is about 750,000 rollouts and 81B to 111B tokens per model, for $2.6M of compute on Pro.
- If the training pool were only the released tasks, each task would have been attempted about 100 times. The real pool was larger, since the release leaves out some domains.

The knowledge came earlier. MiMo-V2.6-Pro was pretrained on 30T tokens and Flash on 48T, then mid-trained on agent trajectories, then briefly fine-tuned. RL teaches the model to use what it already knows across long tasks. It does not teach it Python or tax law.

Xiaomi's small open model shows the split. They distilled MiMo into Qwen3.5-9B, then ran RL on the released environments.

<a href="/mimo-rl/#/grading"><img src="/assets/img/blogs/mimo-rl/fig-ninebee.png" alt="Scores of the 9B model before distillation, after distillation and after RL" width="100%"></a>

Distillation gives the bigger jump on 8 of the 11 benchmarks. RL on the released tasks then improves all 11, by 2.8 to 15.7 points. The biggest RL gains are on Terminal Bench 2.1 (37.1 to 52.8) and the cyber benchmark (31.3 to 47.0).

Three more things make a small task set go further.

- The reward has to be right. A wrong reward repeated 100 times per task teaches the wrong thing 100 times. So Xiaomi audits each code task with 4 agent attempts and an auditing agent, reruns the tests 8 times to catch flaky ones, and lets a "hack agent" attack every environment until it finds no more exploits. During training, confirmed hacks stayed under 2% of trajectories. The released images do not fully match this, as the section on problems below shows.
- The grader gives more than pass or fail. For code, an agent grader reads all 16 rollouts together and ranks the passing patches, so a clean fix earns more than a messy one that also passes. The paper says that without this, policies drifted toward swallowing exceptions and relaxing validation to pass tests.
- The training mix is varied. One run mixed coding, office work, design, context following and cyber, across four different agent harnesses. On DeepSWE, the score on three harnesses the model never trained in rose from about 50% to 66%.

Over the RL run, MiMo-V2.6-Pro went from 58.4 to 72.6 on DeepSWE.

## What the team cares about

Reading the paper and the training code side by side, a few habits stand out. The [explorer](/mimo-rl/#/tastes) has 17 of them with quotes and links. These are the ones I found most interesting.

- Each model got a single RL run that mixed all domains in every batch. They named the experiments section "You Only RL Once" and built a scheduler to keep each domain's share steady, even though rollout times differ 66 times between sources.
- They do not train inside Claude Code or Codex, because the extra prompts in production harnesses sit outside the reward. They train in four tiny agent loops of their own and keep the real harnesses for testing.
- Grading is a budget line. 12.7% of Pro's RL compute went to graders, which are agents that open the environment and read the whole trajectory.
- Tests stay in charge. For code, the reward is the test result times a solution score times a behavior score. A failed test always gives zero, so a nice-looking patch can never rescue a wrong one.
- An infrastructure failure never counts as a zero. If a pod dies or a judge times out, the rollout is masked, because a zero would teach the model that the failure was its own. In the webdev grader, a broken row gets the group's mean reward, which [removes it from the gradient](https://github.com/XiaomiMiMo/verl/blob/a2ad9f6160b03ff2d47e59832bfb6b289f37c917/recipes/design/webdev/group_reward.py#L47-L51) without any change to the trainer.
- A broken web page scores zero, not half. The [code comment](https://github.com/XiaomiMiMo/verl/blob/a2ad9f6160b03ff2d47e59832bfb6b289f37c917/recipes/design/grader_service/src/design_grader/service/runtime_gate.py#L18-L39) explains why: a penalty factor "is tradable against the visual score", so the model would learn to accept broken pages that look good.
- They measure the judge's bias. The webdev judge sees the screenshots in the order of a Williams Latin square, which they [measured](https://github.com/XiaomiMiMo/verl/blob/a2ad9f6160b03ff2d47e59832bfb6b289f37c917/recipes/design/grader_service/src/design_grader/service/group_pick.py#L24-L30) cuts the first-position bias from about 0.28 votes to 0.03.
- The music scorer rewards a piece for being typical. It gives full marks when each statistic sits inside the middle 80% of human music, and less when it is extreme in either direction.

## What is wrong with it

I checked every part I could run without the original infrastructure. For the general tasks, I ran every code check with Xiaomi's own released grader function on untouched copies of the environments. The [Issues page](/mimo-rl/#/findings) has all 20 findings with links to the rows. These are the main ones.

### The code images still hold the fixes

The paper says Xiaomi kept each repository's git history only up to the task's base commit, and removed build outputs that could reveal the fix. The released images do not match that.

- In the images with the repository in `/testbed`, the builders cloned the upstream project and reset it to the base commit. The later commits are still in git's object store, and `git log --reflog` shows them.
- In the images with the repository in `/workspace/repo`, the upstream branches and tags are still there, so `git diff HEAD main` shows the code the task removed.

A Claude subagent audited 16 code images, and all 16 let an agent read commits from after the base. In the 6 it inspected closely, the exact fix was there every time. In the Astro task, `git log --reflog --grep trailingslash` finds the upstream fix, and applying it makes the hidden tests pass. Two images also hold compiled copies of the fixed code. I checked one image myself: its reflog points at the upstream tip, `git fsck` lists 934 leftover commits, and the compiled Java class already has the method the task asks for.

This is the exact shortcut the paper warns about in its reward hacking section. Xiaomi's released harness does check for leftover history, but only through branches and tags. So it refuses to start the `/workspace/repo` tasks, and it misses the reflog leaks in the `/testbed` tasks. If you train on these images, turn on the harness option `git_leak_prevention: strip`, and clean out build folders such as `target/` and `__pycache__`.

### Cyber training tasks overlap CyberGym

Both sets come from ARVO, and 135 of the 1,000 cyber training bugs share an id with [CyberGym](https://huggingface.co/datasets/sunblaze-ucb/cybergym), where the paper reports 94.0 for Pro and 95.1 for Flash. The paper says it fixed some CyberGym environments, but not whether it removed training bugs. I cannot tell whether these tasks were in the Pro and Flash runs. Anyone comparing CyberGym scores should exclude these ids.

### The music reward never checks the prompt

Every prompt asks for a key, tempo, meter, instruments and length, but the released scorer only measures how human-like the notes are. The code says it plainly: the scorer "looks only at the ABC the policy emitted", and grading instruction-following is something "this scorer does not do".

I scored pieces with the unmodified scorer. Six pieces Claude wrote to follow their prompts scored 0.60 to 0.89. A piece of uniformly random notes, split into a treble and a bass voice, scored 0.77, which is higher than five of the six. Formatting matters far more than the music: one blank line inside the notation drops the reward to 0.

### 25 general tasks cannot reach full reward as released

The code checks in 51 tasks compare the database with a backup file called `state.db.pinned_backup`. That file is not in the release, and the released harness never creates it. Without it, the check crashes and scores 0.

I ran every check with and without the backup. In 28 tasks, 43 rubric items fail only because the file is missing, and 25 tasks can no longer reach a reward of 1.0. The fix is one line: copy each database before the agent starts.

### Many general tasks pay out for doing nothing

<a href="/mimo-rl/#/grading"><img src="/assets/img/blogs/mimo-rl/fig-donothing.png" alt="Reward paid to an agent that does nothing, general tasks" width="100%"></a>

With no answer and no changes, every LLM item scores 0, but many code checks still pass, because they only check that nothing was broken. 172 of the 925 general tasks pay out some reward for doing nothing. The free reward averages 0.26 in those tasks and reaches 0.6.

Part of this is by design, since a do-no-harm check should pass when nothing changes. But these checks carry the same weight as the real items, so a do-nothing rollout starts well above zero. In 30 tasks, a check marked critical already passes before the agent starts. In one of them, 3 of 5 critical checks look for values the untouched database already holds.

### A small test run on the code tasks

I ran Claude on 8 code tasks in their own Docker images, with the network off and without looking at the hidden tests. I graded them the way Xiaomi's harness does, which resets the test files and then applies the hidden patch. Claude solved all 8. In all 8 tasks, the hidden tests fail on the untouched repository, so none of them hands out free reward.

The run also turned up small problems:

- In one task, the hidden test calls a method named `Core` that the prompt never mentions.
- In two tasks, the image already has the npm packages that the reference fix adds.
- One prompt describes a crash that the original code already catches.

Eight tasks is a small sample, so I cannot give rates from it.

### Smaller issues

- 501 cyber tasks share their exact target, the bug type, function and file, with another task. 26 target an abort in the fuzzer's setup function, which runs before any input is read, so any input may trigger it. I did not run the cyber tasks, so I could not confirm this.
- 481 music prompts state a length that does not match their tempo. The stated length depends only on the bar count, so 64 bars at 172 BPM, under a minute of music, becomes "about three minutes".
- 74 website prompts tell the agent to use an attached screenshot or logo that is not in the dataset.
- 41 website prompts still start with the label "Prompt:".
- Some rubric weights use field names the grader ignores. In one task, a sanity check that passes by default carries half of the total weight.
- The released general grader falls back to gpt-4o-mini as the judge when none is set. The paper used Xiaomi's own model.
- 239 code tasks run `npm install` or `pip install` while grading, which needs the network or a cache.
- 2 of the 6 code images we inspected cannot run their hidden tests without the network, and one of the two terminal images we checked is missing packages that a correct fix needs.

The good news is that no code task copies a SWE-bench Verified or SWE-bench Pro problem, and I found no near-duplicate prompts outside the templated music set.

## What is it worth

I priced the set two ways: what a lab would pay vendors for similar tasks, and what it would cost to build again. Public prices are thin. The best source is Epoch AI's [interviews](https://epoch.ai/gradient-updates/state-of-rl-envs) with people at environment startups and labs, who put most RL tasks at $200 to $2,000 each.

- At vendor prices, the middle case is about $1.9M, or $1.4M after a discount for what the release leaves out: reference solutions, rollouts and pass rates.
- To rebuild, the middle case is about $2.0M, and most of that is for building the pipelines rather than for compute.
- The range is wide, from about $0.3M to $7.7M, because the prices come from interviews and my own assumptions.

Almost all of the value is in the 2,698 code tasks and the 989 general and terminal tasks. The cyber tasks are cheap to rebuild, because ARVO already reproduces the bugs. The webdev and music prompts are worth little on their own, and their value is in Xiaomi's grader code. The [Value page](/mimo-rl/#/value) has every assumption and source.

For scale, Xiaomi spent $2.6M on the RL compute for Pro alone.

## How I did this

I downloaded the parquet files, the 925 general environments and the list of 3,764 Docker images, and read the paper and Xiaomi's training code at commit `a2ad9f6`. I parsed every row, ran the general graders on untouched environments, compared ids and problem statements with CyberGym, SWE-bench Verified and SWE-bench Pro, and embedded every prompt to build the map. Claude subagents helped with parts of this, e.g., reading the training code, auditing the Docker images and running the 8 code tasks. I checked their key claims against the sources.

I did not run the cyber tasks, and I did not rerun Xiaomi's training. The release is also a subset of what the paper trained on, so a problem in the release does not always mean a problem in MiMo-V2.6.

Everything is in the [explorer](/mimo-rl/). If you find something I got wrong, tell me.
